## FINDING 1 — the `.vault` footer digest is unkeyed

**Severity: low.** Not exploitable for forgery or disclosure. It is a gap between what the
format's integrity actually rests on and what a reader of the code would assume.

### What it is

`vault_file.dart:275`

```dart
final footerHash = _sodium.crypto.genericHash.createConsumer(outLen: 32);
```

An **unkeyed** BLAKE2b over everything above the footer. Anybody can recompute it. It
detects accidental corruption; it provides no authenticity.

### The concrete attack, and where it actually stops

An attacker with write access to somebody's `.vault` file:

1. Deletes the last *N* chunks.
2. Rewrites the `chunkCount` in the footer to match — the reader checks this
   (`vault_file.dart:1008`), so it has to be consistent.
3. Recomputes the footer digest, which needs no key.

Every surviving chunk is still individually valid: right key, right nonce, right AAD. The
index-in-nonce check passes because the indices are still sequential from zero.

**What stops it is gzip.** The body is a gzip stream, and a truncated one fails at its CRC32
and length trailer. So the restore is refused.

**That is a real defence and it is not a cryptographic one.** It is a property of a
compression container that happens to be in the pipeline, it is not written down anywhere as
load-bearing, and it would evaporate the day somebody changes the compression — for example
to make backups seekable, which is a perfectly reasonable future change nobody would connect
to this.

### What is NOT vulnerable, and it is worth being precise

- **Reordering: properly caught.** The chunk index is bound into the nonce *and checked on
  the way back* (`vault_file.dart:977`). The test even repairs the footer hash first, so it
  proves the index check is doing the work rather than the digest. This is exactly right and
  the comment beside it makes the argument correctly.
- **Splicing from another backup: impossible.** Different file key.
- **Forging a chunk: impossible.** No key.
- **Header tampering: caught.** The header is the AAD on the wrapped key *and* on every
  chunk, so rewriting `memLimit` to 1 breaks the tag rather than weakening the KDF. This is
  the single most important thing in the format and it is done correctly.

### The fix, and why I have not applied it

Two clean options:

1. **Key the footer digest** — `genericHash` with the file key, or a `KeyPurpose`-derived
   subkey of it. The digest becomes a MAC and truncation fails cryptographically.
2. **Bind the total to the last chunk's AAD** — `header ‖ u64(chunkCount)` on the final
   chunk only. Strictly better, because it makes the end of the file a thing the key
   attests to.

Either is small. **Both change the file format**, and `04-technical/BACKUP-FILE-FORMAT.md`
is a specification with v1 and v2 readers that must keep working — `CLAUDE.md` says the doc
changes before the code does. It is also, honestly, **not urgent**: the practical impact is
a denial of service against a backup file by somebody who could equally well delete it.

**Recommended: option 2, as format v3, next time the format is opened for another reason.**

## Everything else the prompt asks about

### Crypto correctness

| | Verdict |
|---|---|
| **Nonce or IV reuse** | **Absent.** `wrapKey` draws a fresh 24-byte nonce from `randombytes` per wrap. Attachments use libsodium's `secretStream`, which owns its own nonce sequence. The backup body uses a 16-byte random prefix ‖ 8-byte counter — a fresh prefix per file, so two backups never share a nonce even under the same key. |
| **Nonce from a counter/timestamp alone** | **Absent.** The backup counter is *combined with* a random prefix, which is the correct construction. |
| **One key for two purposes without domain separation** | **Absent.** `deriveSubkey` uses libsodium `crypto_kdf` with context `lamplght` and a permanent numeric id per purpose (database 1, attachment index 2, thumbnails 3). Recovery uses a domain-separated BLAKE2b — `lamplight/recovery-kek/v1`. |
| **Seeded PRNG for anything secret** | **Absent.** Three seeded generators exist and all three are in `design/` — the paper grain and the star catalogue. Rule 6 was deliberately narrowed on 22 August to permit exactly this; a fixed seed is *required* there or the texture shimmers between launches. Nothing in `crypto/`, `storage/` or `backup/` uses one. |
| **Argon2id parameters weaker than documented, or from an untrusted source** | **Absent, and defended twice.** Unlock reads `keyring.memLimit/opsLimit` (`vault.dart:283`, `:397`), never the compile-time defaults — those are used only when *creating*. And the keyring header is the AAD on the wrapped DEK, so editing the parameters on disk breaks the tag instead of weakening the KDF. |
| **Encrypt-then-MAC ordering; tags verified before plaintext is used** | **Correct.** Everything goes through libsodium AEAD, which verifies the Poly1305 tag before returning plaintext. There is no hand-rolled composition anywhere. |
| **Decryption failure swallowed, logged-and-continued, or partial plaintext returned** | **Absent.** Every `catch (_)` on a decrypt path *rethrows* as a plain-language error — `vault_file.dart:550`, `:589`, `:991`. None returns partial output, none continues. The attachment store yields a chunk only after it authenticates. |
| **Timing side channels on passcode/tag/key comparison** | **Absent, structurally.** There is no stored passcode hash to compare against — a wrong passcode is detected by the AEAD unwrap failing. There is nothing to compare in variable time. The attempt limiter compares only counters and timestamps. |
| **SQLCipher misconfiguration** | **Correct.** The key is passed as `x'<hex>'`, which makes SQLCipher use it **directly** rather than running its own PBKDF2 over it — right, because the key already came from Argon2id via the hierarchy. `pubspec.yaml` pins `sqlite3` to the `sqlcipher` source with a comment saying the vault silently becomes unencrypted if that is changed. Defaults for SQLCipher 4 (HMAC-SHA512 per page, 256 000 KDF iterations for passphrases) are untouched, and the plaintext header is not enabled. |

### Key lifecycle

| | Verdict |
|---|---|
| **Key material in a Dart `String`** | **Two, both known, both bounded — see "acknowledged limits" below.** No *derived key* is ever a String. |
| **Keys zeroed on lock / background / timeout** | **Correct.** `Vault.lock()` closes the database **before** disposing the DEK, so no in-flight query outlives the key, then disposes the DEK and the session backup key and drops the salt. |
| **Keys reachable after lock** | **No path found.** `_dek`, `_db`, `_attachments`, `_sessionBackupKey` are all nulled. libsodium `SecureKey` uses guarded, locked allocations wiped on dispose. The honest caveat about a managed runtime is in `SECURITY-ARCHITECTURE.md` §8 and is correct. |
| **Biometric key surviving a new fingerprint enrolment** | **Absent — handled.** `BiometricVault.kt:229` sets `setInvalidatedByBiometricEnrollment(true)` alongside `setUserAuthenticationRequired(true)`. This is the classic bug in this area and it is closed. |
| **The backup reusing the vault's DEK** | **Absent.** `vault_file.dart:238` generates a **fresh** AEAD key per backup and wraps it under the passcode-derived backup KEK (and, for v2, under KEK-R as well). The DEK never leaves the vault. |

### Logic

| | Verdict |
|---|---|
| **A path reaching note content without a successful unlock** | **None found.** Content is reachable only through `VaultDatabase`, which only exists between `unlock` and `lock`, and through `AttachmentStore`, whose per-file keys live in that database. |
| **Race between lock and an in-flight write** | **Handled, and it was a real bug once.** `Vault.whileSettling` holds the lock for a bounded 4 seconds for a write already committed to; `onBackgrounded` awaits it. `settling_test.dart` pins both directions — that it waits, and that it still locks. Extended to the composer on 28 August. |
| **Auto-lock defeated by keeping a screen open or a long operation running** | **Partially by design, and correctly bounded.** `expectSystemReturn` holds the vault open for up to **three minutes** across a camera or picker excursion — necessary, because taking a photograph leaves the app — and it is backed by a timer that locks anyway if the user never returns. `whileSettling` is 4 seconds. Neither is unbounded. |

## Acknowledged limits — not findings, but they should not be discovered later

1. **The passcode is a Dart `String`.** It arrives from a `TextField` and Flutter offers
   nothing else. Strings are immutable and cannot be wiped, so it persists until the
   collector reclaims it. **No fix is available in this framework.**
   `SECURITY-ARCHITECTURE.md` §8 states it.
2. **The SQLCipher key becomes a hex `String`.** Unavoidable — the pragma takes text. It is
   built **inside the worker isolate** (`database.dart`, `_prepare`), so it never exists on
   the UI heap, and closing the database destroys that isolate and its heap with it. This
   was already improved once for exactly this reason and the reasoning is written down.
3. **The attempt limiter is app-enforced and defeatable on a rooted phone.** The file says
   so itself, and correctly: *"the delay is not what protects the vault — Argon2id is."*
   An attacker capable of an offline attack copies `/data/data` and never meets the counter.
   Stating it is the right posture.

## What this audit did not do

- **No decompilation of the release DEX.** The obfuscation argument in `build.gradle.kts` is
  that readability was never the defence, and it is right; `PERIMETER-AUDIT.md` covers the
  artifact.
- **No fuzzing of the `.vault` parser.** `vault_file_test.dart` breaks the file in five
  specific ways and each is refused, which is targeted rather than exhaustive. A structured
  fuzzer over the header lengths would be the next real step, and nobody has asked.
- **No live memory inspection.** Whether a key is genuinely gone from RAM after `lock()`
  cannot be settled from source in a managed runtime, and §8 already declines to claim it.
